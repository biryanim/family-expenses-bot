# AGENTS.md

Сервис учёта семейных расходов: Telegram-бот с ИИ-агентом и веб-панель для главы семьи.

## Что делает
- **Бот.** Член семьи пишет обычным текстом («кофе 350», «такси 1200 вчера», «удали такси»). ИИ-агент через tool calling добавляет, показывает, изменяет и удаляет траты. Без кнопок и команд.
- **Веб-панель.** CRUD над тратами всех членов семьи с фильтрами по члену семьи, периоду и категории. Работает через REST API. Авторизации нет.

## Стек
- Go (версия из `go.mod`), один бинарь: REST API и бот в одном процессе.
- HTTP: `github.com/go-chi/chi/v5`.
- REST API spec-first: контракт в `api/openapi.yaml` (OpenAPI 3.0), код сервера и модели генерируются `oapi-codegen` (strict server под chi). TS-типы фронтенда генерируются из той же спецификации через `openapi-typescript`.
- БД: PostgreSQL, драйвер `github.com/jackc/pgx/v5`, SQL пишется вручную (без ORM).
- Миграции: goose CLI (`github.com/pressly/goose/v3`), SQL-файлы в `migrations/`. Приложение их не применяет: в compose это делает сервис `migrate` до старта `app`, локально — `make migrate-*`.
- Telegram: `github.com/go-telegram/bot`, long polling.
- LLM: OpenAI-совместимый Chat Completions API с tool calling, свой тонкий HTTP-клиент. `base_url`, `api_key`, `model` задаются в конфиге.
- Фронтенд: React + Vite + TypeScript, TanStack Query. В compose отдаётся через nginx.
- Запуск: `docker compose up`.

## Структура

```
cmd/app/main.go            точка входа, сборка зависимостей
api/openapi.yaml           спецификация REST API
migrations/                SQL-миграции goose
internal/
  entity/                  сущности, без зависимостей от других пакетов проекта
  usecase/                 бизнес-логика; интерфейсы зависимостей объявляются здесь
  database/postgres/       подключение к PostgreSQL
  database/repository/     доступ к данным (ручной SQL)
  transport/http/          хендлеры REST API
  transport/telegram/      обработчик сообщений бота
  agent/                   цикл ИИ-агента и инструменты
  llm/                     клиент LLM
  config/                  конфиг из переменных окружения
web/                       фронтенд
mock/                      сгенерированные gomock-моки (go generate)
```

## Архитектурные правила
- Зависимости направлены внутрь: `transport/*`, `agent` → `usecase` → `entity`. `database/repository` реализует интерфейсы из `usecase`.
- Транспорт и агент не обращаются к `database/*` напрямую.
- Интерфейсы объявляются на стороне потребителя и только там, где нужны подмена или тесты (репозиторий, LLM-клиент, часы).
- Бизнес-правила (валидация суммы и категории, «последняя трата») живут в `usecase` и общие для REST и бота.

## Изменение API
- Порядок всегда такой: правка `api/openapi.yaml` → `go generate ./...` → код. Не наоборот.
- Сгенерированные файлы (`*.gen.go`, сгенерированные TS-типы) руками не правятся и коммитятся в репозиторий.

## Доменные правила
- Категории фиксированные: еда, транспорт, жильё, развлечения, здоровье, покупки, другое. Нераспознанная категория → «другое».
- Сумма хранится как `int64` в копейках. Никаких float для денег.
- Дата траты (`spent_at`) по умолчанию сегодня. Относительные даты («вчера», «за неделю») агент считает от текущей даты, которую получает в промпте.
- Член семьи — любой пользователь Telegram, который писал боту. Глава семьи — тот, кто открыл веб-панель.

## Безопасность: изоляция трат
- В боте каждый пользователь видит и меняет только свои траты.
- `user_id` берётся из Telegram-апдейта в `transport/telegram` и передаётся в инструменты агента кодом. В схемах инструментов параметра пользователя нет, модель не может его задать.
- Обращение к чужой трате ведёт себя как к несуществующей.
- Любое изменение в этой части сопровождается тестом «пользователь A не видит, не меняет и не удаляет траты B».

## Код
- Форматирование `gofmt`, перед коммитом `go vet ./...` и `go test ./...`.
- Идентификаторы на английском. Комментариев в коде нет; единственное исключение — директивы `//go:generate`.
- `context.Context` первым аргументом во всём, что ходит в БД, сеть или LLM.
- Секреты только через env, в репозитории есть `.env.example`, `.env` в `.gitignore`.
- Все интерфейсы-зависимости пакета лежат в его `deps.go`.
- Один метод — одна самостоятельная функция в своём файле: `CreateExpense` → `create_expense.go`. Приватных переиспользуемых хелперов нет, методы не вызывают друг друга, повтор кода допустим.
- Имена методов называют действие и сущность: `CreateExpense`, `ListExpensesForUser`, а не `Create`, `List`. Конструктор — `New`.

## Ошибки
- Ошибка оборачивается именем вызова, который упал, а не метода, в котором это случилось: `fmt.Errorf("r.pool.QueryRow.Scan: %w", err)`, `r.pool.Query`, `r.pool.Exec`, `rows.Scan`, `rows.Err`, `pgxpool.New`.
- «Не найдено» и нарушения доменных ограничений возвращаются голым sentinel из `internal/entity/errors.go` (`entity.ErrNotFound` и т.п.), без обёртки.
- Проверка типа ошибки — `if pgErr, ok := errors.AsType[*pgconn.PgError](err); ok`, а не `errors.As` с заранее объявленной переменной.
- Ошибки не теряются и не логируются дважды: кто возвращает ошибку, тот её не логирует.

## Тесты
- Unit-тесты рядом с кодом (`*_test.go`), по файлу на метод (`create_expense_test.go`).
- Моки — gomock, генерируются `go generate ./...` директивами в `deps.go` в корневой `mock/` (пакет `mock`): `//go:generate go tool mockgen -source=./deps.go -destination ../../../mock/<name>.go -package mock`; сторонние интерфейсы (`pgx.Row`, `pgx.Rows`) — отдельными директивами. `mockgen` подключён как `tool` в `go.mod`.
- Тесты пакета — testify `suite` в пакете `<pkg>_test`: `Suite` с `ctrl`, моками и тестируемым объектом, `SetupTest`/`TearDownTest`, `Test<Pkg>` запускает `suite.Run`.
- Один кейс — один метод `TestМетод_Кейс` (`_Success`, `_NotFound`, `_ScanError`, …): Arrange (`ctx`, моки через цепочку `EXPECT()`), Act, Assert по полям результата. Таблица с `s.Run` — только для однотипных комбинаций (например, фильтров).
- Sentinel проверяется `s.Equal(entity.ErrNotFound, err)` и нулевым результатом; обёрнутая ошибка — `s.ErrorIs` и `s.Contains(err.Error(), "<вызов>")`.
- LLM в тестах подменяется моком, реальные запросы к провайдеру в тестах не делаются.

## Команды
- Генерация: `go generate ./...` (в том числе моки: `//go:generate go tool mockgen` в `deps.go`, моки кладутся в корневой `mock/`)
- Сборка: `go build ./...`
- Тесты: `go test ./...`
- Проверка: `go vet ./...`
- Запуск всего: `docker compose up --build`
- Миграции: `make migrate-up`, `make migrate-down`, `make migrate-reset`, `make migrate-status`, `make migrate-create name=<name>`

## OpenSpec
Работа ведётся через OpenSpec: изменения в `openspec/changes/`, актуальные спецификации в `openspec/specs/`. Команды `/opsx:propose`, `/opsx:apply`, `/opsx:archive`. Артефакты OpenSpec пишутся на русском.
