# Spec Delta

## Purpose

Описывает запуск всего сервиса (PostgreSQL, миграции, приложение с ботом и REST API, веб-панель) одной командой `docker compose up` из конфигурации в `.env`, без ручных шагов, кроме заполнения секретов.

## ADDED Requirements

### Requirement: Запуск всего сервиса одной командой
При наличии заполненного `.env` команда `docker compose up --build` на машине без ранее собранных образов и томов SHALL собрать образы бэкенда и панели и поднять PostgreSQL, применить миграции, запустить приложение (бот и REST API) и панель без других ручных шагов.

#### Scenario: Чистая машина
- **WHEN** на машине только Docker, репозиторий и `.env`, созданный из `.env.example`, и выполняется `docker compose up --build`
- **THEN** сервисы `postgres`, `app` и `web` работают, `migrate` завершился с кодом 0, а бот отвечает на сообщения в Telegram

#### Scenario: Нет `.env`
- **WHEN** файла `.env` нет
- **THEN** `docker compose up` завершается с понятной ошибкой об отсутствующих значениях и не запускает приложение с пустыми секретами

### Requirement: Порядок старта сервисов
Миграции SHALL запускаться только после того, как PostgreSQL прошёл healthcheck, приложение SHALL стартовать только после успешного завершения миграций, а панель SHALL стартовать после приложения.

#### Scenario: БД ещё не готова
- **WHEN** PostgreSQL только запускается и не принимает соединения
- **THEN** `migrate` и `app` ждут успешного healthcheck БД и не падают из-за раннего старта

#### Scenario: Миграция упала
- **WHEN** `migrate` завершился с ненулевым кодом
- **THEN** `app` и `web` не запускаются, а причина видна в логах `migrate`

### Requirement: Сохранность данных БД
Данные PostgreSQL SHALL храниться в именованном томе и переживать остановку и повторный запуск сервисов. Удаляться они SHALL только явной командой удаления томов.

#### Scenario: Перезапуск
- **WHEN** трата создана, затем выполнены `docker compose down` и `docker compose up`
- **THEN** трата по-прежнему возвращается из бота и из панели

#### Scenario: Повторный запуск миграций
- **WHEN** `docker compose up` выполняется на БД, где миграции уже применены
- **THEN** `migrate` завершается с кодом 0, не меняя схему и данные

### Requirement: Панель и бот на общей БД
Веб-панель SHALL быть доступна на порту хоста `WEB_PORT` (по умолчанию 3000) и обращаться к REST API приложения через собственный origin по пути `/api/`. Бот и панель SHALL работать с одной и той же базой.

#### Scenario: Трата из бота видна в панели
- **WHEN** пользователь пишет боту «кофе 350», затем открывается `http://localhost:3000`
- **THEN** трата «кофе» на 350 ₽ есть в списке панели

#### Scenario: Трата из панели видна боту
- **WHEN** в панели создана трата пользователя, и этот пользователь просит бота показать траты
- **THEN** бот показывает созданную трату

#### Scenario: Нестандартный порт API
- **WHEN** в `.env` задан `HTTP_PORT=9090`
- **THEN** панель всё равно получает ответы от API через `/api/`

### Requirement: Конфигурация и секреты через `.env`
Вся конфигурация сервисов SHALL задаваться через `.env` по образцу `.env.example`. `.env` SHALL быть исключён из репозитория и из контекста сборки образов, значения секретов SHALL NOT попадать в слои образов.

#### Scenario: Секреты вне образа
- **WHEN** образы собраны при заполненном `.env`
- **THEN** `TELEGRAM_BOT_TOKEN`, `LLM_API_KEY` и пароль БД не содержатся ни в одном слое образов `app`, `migrate` и `web`

#### Scenario: Образец конфигурации полон
- **WHEN** `.env.example` копируется в `.env` и в нём заменяются значения `replace-with-*`
- **THEN** этого достаточно для запуска, и все переменные, нужные compose, описаны в `.env.example`
