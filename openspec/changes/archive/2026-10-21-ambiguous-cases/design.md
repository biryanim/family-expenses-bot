# Design

## Context

- `agent.HandleMessage(ctx, userID, text)` на каждое сообщение собирает историю заново: `[system, user]`. Между сообщениями ничего не хранится.
- В `systemPrompt` (`internal/agent/agent.go`) есть два правила, которые прямо противоречат задаче: «выбери самую позднюю по дате подходящую трату» и «Уточняющих вопросов не задавай: следующее сообщение придёт без контекста этого диалога».
- `go-telegram/bot` обрабатывает апдейты несколькими воркерами (`defaultWorkers`, горутины `waitUpdates`). `HandleMessage` вызывается конкурентно, в том числе для одного и того же пользователя.
- `list_expenses` сортирует по `spent_at DESC, id DESC`, поэтому порядок трат стабилен между вызовами. На этом держится выбор «второе».
- `get_last_expense` уже возвращает трату с наибольшим `id` (`ORDER BY id DESC LIMIT 1`), то есть последнюю созданную. Код здесь менять не нужно.
- `add_expense` требует `amount` в схеме. Нет суммы — нет вызова, но модели нужно разрешить спросить.
- `README.md` в репозитории нет.

## Goals / Non-Goals

**Goals:**
- Уточнения через короткую историю диалога в памяти процесса, изолированную по `user_id`.
- Правила промпта для каждого неоднозначного случая из задачи.
- По тесту на каждый случай: детерминированные тесты с mock-LLM плюс ручная проверка на реальной модели.

**Non-Goals:**
- Хранение истории между перезапусками, история для нескольких инстансов.
- Кодовый «предохранитель», запрещающий удаление без подтверждения (машина состояний «ожидающее действие»). См. решение 1, альтернатива 3.
- Кнопки и inline-клавиатуры: AGENTS.md требует «без кнопок и команд».
- Изменения API, БД, конфига.

## Decisions

### 1. История — в памяти процесса, только текст реплик

Храним последние 6 реплик на пользователя: `RoleUser` с его текстом и `RoleAssistant` с финальным ответом. Реплики старше 15 минут игнорируются. Для ответа на уточнение этого хватает: вопрос бота содержит сумму и дату каждого варианта, и модель на «второе» заново вызывает `list_expenses` и однозначно находит трату.

Рассмотренные альтернативы:
1. **Redis.** Пережил бы перезапуск и дал бы общий стейт для нескольких инстансов. Но инстанс у нас один и другим быть не может: long polling не допускает двух получателей, второй получит `409 Conflict`. А потеря контекста при перезапуске безопасна: бот просто переспросит, ничего не удалив. При этом Redis — это новый сервис в compose, новая зависимость `go-redis`, конфиг и обработка его недоступности. Цена несоразмерна выгоде.
2. **Таблица в PostgreSQL.** Те же аргументы, плюс миграция и очистка старых строк.
3. **Структурированное «ожидающее действие»** (код сохраняет `{op, candidates}`). Самый строгий вариант, но под каждый тип неоднозначности нужна своя ветка, и «кофе без суммы» в эту модель не ложится. История закрывает все случаи одним механизмом.
4. **История вместе с tool-вызовами.** Модель помнила бы `id` кандидатов, но токенов уходит кратно больше. Кроме того, при обрезке по лимиту нельзя разрывать пару «assistant с `tool_calls` → tool-результаты», иначе провайдер вернёт 400. Выигрыш на фоне повторного `list_expenses` минимальный.
5. **Telegram ForceReply** (контекст из `reply_to_message`). Ломается, как только пользователь отвечает обычным сообщением, а не reply.

### 2. Интерфейс в `agent/deps.go`, реализация — пакет `internal/agent/history`

```go
type ConversationStore interface {
	ListMessagesForUser(userID int64, now time.Time) []Message
	AppendMessagesForUser(userID int64, now time.Time, messages ...Message)
}
```

- Интерфейс нужен, чтобы разорвать цикл импортов: реализации нужен `agent.Message`, агенту — хранилище. Так же сейчас устроены `ToolExecutor` и пакет `tools`.
- `ctx` и `error` в сигнатурах нет: хранилище не ходит ни в БД, ни в сеть, ни в LLM, поэтому правило о `context.Context` здесь не применяется.
- `now` передаётся параметром. Это не интерфейс часов: агент уже вычисляет `now := time.Now()` для даты в промпте и передаёт это же значение. Тесты TTL в пакете `history` подставляют конкретные моменты без `time.Sleep`.
- Пакет `history` лежит внутри `internal/agent/` по аналогии с `internal/agent/tools/`, то есть в пределах «цикл ИИ-агента и инструменты» из AGENTS.md. Новых каталогов верхнего уровня нет.
- Структура: `history.go` (тип `History`, `New`, константы `maxMessages = 6`, `ttl = 15 * time.Minute`), `list_messages_for_user.go`, `append_messages_for_user.go`, тесты по файлу на метод и `history_test.go` с `Suite`.

```go
type History struct {
	mu      sync.Mutex
	dialogs map[int64][]entry
}

type entry struct {
	message agent.Message
	at      time.Time
}
```

- `ListMessagesForUser` под мьютексом возвращает копию сообщений пользователя, у которых `now.Sub(at) <= ttl`.
- `AppendMessagesForUser` под мьютексом выбрасывает устаревшие записи, добавляет новые с `at = now` и оставляет последние `maxMessages`. Агент всегда пишет пару «user + assistant», поэтому при чётном лимите история всегда начинается с реплики пользователя.
- Память не растёт бесконечно: ключей не больше, чем членов семьи, у каждого не больше 6 записей. Фоновая очистка не нужна.

### 3. Встраивание в агента

- `agent.New(llm LLMClient, history ConversationStore, tools ...ToolExecutor)`, поле `history` в `Agent`. Сигнатура меняется, вызовы в `cmd/app/main.go` и `agent_test.go` правятся.
- `HandleMessage` собирает `messages = [system] + history.ListMessagesForUser(userID, now) + [user text]`.
- После успешного финального ответа агент вызывает `history.AppendMessagesForUser(userID, now, user, assistant(answer))`. На любом `return` с ошибкой (модель, инструмент, `ErrEmptyAgentReply`, `ErrAgentStepLimit`) записи нет, поэтому `replyFailure` из `transport/telegram` в историю не попадает.
- `userID` — тот же, что уходит в инструменты, то есть из `msg.From.ID`. Модель на ключ истории не влияет.
- Конкурентные сообщения одного пользователя могут прочитать одну и ту же историю и дописать свои пары в любом порядке. Это допустимо: данные не повреждаются, мьютекс защищает `map`.

### 4. Правила системного промпта

Удаляются строки «Изменение или удаление по описанию… выбери самую позднюю…» и «Уточняющих вопросов не задавай…». Добавляются (черновик, формулировку можно подправить при ручной проверке):

> - Изменение или удаление по описанию («удали такси») — сначала list_expenses. Подходит одна трата — измени или удали её по id. Подходят несколько — ничего не меняй и не удаляй: перечисли их по номерам в порядке из list_expenses, с суммой и датой, и спроси, какую выбрать. Не подходит ни одна — скажи, что такой траты не нашёл.
> - Если пользователь отвечает на твой вопрос («второе», «та, что за 700»), смотри предыдущие реплики, снова вызови list_expenses и работай с той тратой, которую он однозначно указал. Если выбор по-прежнему неясен — спроси ещё раз, ничего не меняя.
> - Если в сообщении о трате нет суммы («кофе») — не вызывай add_expense, спроси сумму. Если в ответ пришла сумма — добавь трату из предыдущего сообщения.
> - Если дату нельзя однозначно понять («на днях», «недавно») — не передавай date и в ответе скажи, что дату не понял и записал на сегодня; исправить можно сообщением «последнее было вчера».
> - Если сообщение не о тратах — не вызывай инструменты, вежливо и коротко скажи, что умеешь: записать трату, показать траты и сумму, исправить или удалить трату.

Правило про «последнее» (`get_last_expense`) остаётся, оно уже соответствует задаче.

### 5. Что и как тестируется

Решения о неоднозначности принимает модель, а в `go test` модель — это mock (AGENTS.md). Поэтому тесты делятся на три уровня:

1. **Промпт.** `TestHandleMessage_SystemPrompt` проверяет, что в системном сообщении есть ключевые фразы новых правил и нет удалённых («самую позднюю», «Уточняющих вопросов не задавай»).
2. **Механика на сценарии.** Mock-LLM разыгрывает правильное поведение модели через настоящие агент, инструменты, usecase и `history.New()`, а `MockExpenseRepository` строгий. Ожидания ставятся только на те обращения, которые допустимы в сценарии. Например, при неоднозначном «удали такси» нет ожиданий `DeleteExpenseForUser`/`UpdateExpenseForUser`, и любая попытка удалить роняет тест. Так проверяется, что история доходит до модели, уточнение работает на втором сообщении, и на ветке уточнения нет необратимых обращений к хранилищу.
3. **Суждение модели.** Ручной прогон на реальной модели по сценариям из спеки, переписка прикладывается к отчёту. Как и в предыдущих изменениях, автоматических eval-тестов с реальным провайдером нет.

В тестах агента используется настоящий `history.New()`, а не `MockConversationStore`: на одном сообщении поведение то же, а многошаговые сценарии читаются проще. Мок всё равно сгенерируется из `deps.go` директивой `mockgen`. TTL и лимит проверяются в пакете `history` с явными `now`.

## Risks / Trade-offs

- [Модель всё равно удалит наугад] → Правило в промпте сформулировано явно («ничего не меняй и не удаляй»), плюс ручная проверка на реальной модели. Кодового запрета нет, это осознанный компромисс (решение 1, альтернатива 3).
- [Две траты с одинаковыми суммой, датой и комментарием: «второе» указывает на трату, неотличимую для пользователя] → Порядок `list_expenses` стабилен (`spent_at DESC, id DESC`), номер из вопроса совпадает с номером при повторном вызове. Для пользователя выбор любой из двух равнозначен.
- [Между вопросом и ответом список трат изменился, например через веб-панель] → Агент заново вызывает `list_expenses` и сверяет трату с описанием из вопроса (сумма и дата), а не только с номером. Если не сходится, переспрашивает.
- [Перезапуск или 15 минут тишины между вопросом и ответом] → Контекст теряется, «второе» модель не поймёт и переспросит. Ничего необратимого не происходит.
- [Ответы бота в истории содержат суммы и даты трат] → История хранится только по `user_id` отправителя, это покрыто тестом «A не видит историю B». История не логируется.
- [Рост токенов] → Не больше 6 коротких реплик на запрос.

## Migration Plan

Деплой обычный, `docker compose up --build`. Миграций и новых переменных окружения нет. Откат — предыдущий образ. История живёт только в памяти, поэтому чистить нечего.
