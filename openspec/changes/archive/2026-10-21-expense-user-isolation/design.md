# Design

## Context

Изоляция сейчас держится на трёх механизмах (подробнее в proposal.md, раздел Why):

1. `transport/telegram.HandleUpdate` берёт `userID` из `msg.From.ID`, а `agent.HandleMessage` передаёт его в `ToolExecutor.Execute(ctx, userID, arguments)`.
2. Каждый инструмент декодирует аргументы с `DisallowUnknownFields`. Ни в одной схеме нет параметра пользователя, это проверяют `*_definition_test.go`.
3. Все `*ForUser`-методы репозитория фильтруют выборку по `AND user_id = $N`. Если строка не найдена или ни одна не затронута, возвращается голый `entity.ErrNotFound`. Инструменты отдают модели на него `{"error":"expense not found"}`.

Каждый слой покрыт тестами только на моке соседнего: агент — с `MockToolExecutor`, инструменты — с `MockToolsUsecase`, репозиторий — с `MockPool`. Тестов, где эти слои собраны вместе, нет. По решению пользователя тесты с настоящим PostgreSQL в этот change не входят.

## Goals / Non-Goals

**Goals:**
- Сквозные тесты «mock-LLM → настоящий `agent.Agent` → настоящие `tools.*` → настоящий `usecase.Usecase` → `MockExpenseRepository`». Они закрывают критерии готовности задачи 09 и сценарии из `specs/expense-agent/spec.md`.
- Проверка неразличимости чужой и несуществующей траты по тому, что реально получает модель, то есть по `Content` tool-сообщений в истории.
- Правило в системном промпте о запросах про чужие траты.

**Non-Goals:**
- Не меняется код изоляции в `usecase`, `repository`, `tools`, `transport/telegram`: дефектов в нём не найдено.
- Интеграционные тесты с PostgreSQL и testcontainers.
- Веб-панель и REST API: там авторизации нет по определению (AGENTS.md), глава семьи видит всех.
- Побочные каналы по времени ответа.

## Decisions

### 1. Сквозные тесты живут в `internal/agent`, в `handle_message_test.go`

Тестируемый вход — `Agent.HandleMessage`, поэтому по правилу «файл на метод» кейсы добавляются в `handle_message_test.go` как `TestHandleMessage_<Кейс>`. В `Suite` из `agent_test.go` появляются поля:
- `repo *mock.MockExpenseRepository`;
- `isolated *agent.Agent`, собранный так же, как в `cmd/app/main.go`: `agent.New(s.llm, tools.NewAddExpense(uc), tools.NewListExpenses(uc), tools.NewGetLastExpense(uc), tools.NewUpdateExpense(uc), tools.NewDeleteExpense(uc))`, где `uc := usecase.New(s.repo)`.

Существующий `s.agent` с моками инструментов остаётся без изменений.

Пакет `agent_test` внешний, поэтому импорт `tools` (который сам импортирует `agent`) и `usecase` не создаёт цикла. Направление зависимостей в production-коде не меняется.

Альтернативы:
- Положить тесты в `tools_test`. Но тогда тестируется не `HandleMessage`, а цикл агента пришлось бы повторять руками.
- Сделать отдельный пакет `internal/isolation`. Это новый каталог вне структуры из AGENTS.md ради одного теста.

### 2. Отсутствие обращений к чужим данным проверяет строгий gomock

На `MockExpenseRepository` ставятся только ожидания с `userA` и конкретными `id`: `GetExpenseForUser(_, userA, idB) → entity.ErrNotFound`, `ListExpensesForUser(_, userA, _) → траты A`. Ожиданий для `userB` нет. Нет и ожиданий для методов без `ForUser` (`GetExpense`, `UpdateExpense`, `DeleteExpense`, `ListExpenses`). Нет `UpdateExpenseForUser` и `DeleteExpenseForUser` для `idB`. Любой лишний вызов роняет тест через `ctrl.Finish()`. Отдельного счётчика вызовов не нужно.

Мок репозитория воспроизводит то, как ведёт себя SQL с `WHERE user_id`: для чужого `id` он возвращает `ErrNotFound`. Это допущение, и проверено оно только тестами репозитория по тексту запроса (`delete_expense_for_user_test.go`, `update_expense_for_user_test.go`, `get_expense_for_user_test.go`). Ограничение осознанное, см. Risks.

Альтернатива — in-memory fake репозитория с проверкой владельца. Отклонена: проверка владельца оказалась бы в тестовом коде, и тест проверял бы fake, а не систему.

### 3. Что реально видит модель, проверяется по истории сообщений

Последний вызов `s.llm.CreateChatCompletion` через `DoAndReturn` копирует `messages`. Утверждения делаются по `Content` сообщений с `Role == agent.RoleTool`, их сопоставляет `ToolCallID`.

Для неразличимости в одном ответе модели два вызова: `update_expense` с `id` траты B и `update_expense` с несуществующим `id`, прочие аргументы одинаковые. Затем проверяются `s.Equal(contentForeign, contentMissing)` и `s.NotContains` суммы, комментария и даты траты B. То же самое делается для `delete_expense`. Так проверяется именно байтовое представление, а не `agent.ToolError` до маршалинга.

### 4. Правило в системном промпте

В `systemPrompt` (`internal/agent/agent.go`) добавляется одна строка в список правил. Черновик:

> - Ты видишь и меняешь только траты того, кто тебе пишет. Траты других членов семьи недоступны. Если просят показать, изменить или удалить чужие траты — ответь, что можешь работать только с тратами самого пользователя, и не выдавай его траты за чужие.

Это правило про UX, а не защита: изоляцию обеспечивает код (решения 1–2), и тесты на mock-LLM не зависят от того, что ответит модель. В `TestHandleMessage_SystemPrompt` добавляется `s.Contains(system, "только траты того, кто тебе пишет")`. Поведение настоящей модели проверяется вручную в реальном диалоге (задача 4.2 в tasks.md). Если модель отвечает плохо, формулировка правится там.

### 5. Переименование битых тестов

`TestDeleteExpense_1OTFOUND`, `TestUpdateExpense_5OTFOUND`, `TestDeleteExpenseForUser_2OTFOUND`, `TestUpdateExpenseForUser_6OTFOUND` в `internal/database/repository` переименовываются в `_NotFound` по конвенции AGENTS.md. Тела тестов не меняются.

## Risks / Trade-offs

- [SQL-фильтр по `user_id` проверяется только текстом запроса в `MockPool`. Если кто-то поменяет SQL на семантически неверный, но строку в тесте обновит вместе с ним, моки этого не поймают] → Решение пользователя: обходимся без интеграционных тестов. Частично ошибку ловит ручная проверка 4.2 вторым пользователем Telegram. Если понадобится настоящая гарантия, отдельным change можно добавить интеграционные тесты репозитория под build-тегом.
- [Мок репозитория в сквозном тесте кодирует ожидаемое поведение БД] → Тест проверяет, что код выше репозитория никогда не просит данные чужого пользователя и не может отличить чужую трату от несуществующей. За то, как ведёт себя сам репозиторий, отвечают его тесты.
- [Модель всё равно может ответить неудачно на «покажи траты пользователя 123»] → Утечки данных это не создаёт: модель получает только траты отправителя. Правило в промпте и ручная проверка снижают риск вводящего в заблуждение ответа.
- [Новые инструменты в будущем могут забыть про `userID`] → Сквозной тест собирает агента теми же конструкторами, что `main.go`. При добавлении инструмента в `main.go` его нужно добавить и в `Suite`. Это следует из уже существующего правила AGENTS.md: изменения в изоляции сопровождаются тестом A/B.
