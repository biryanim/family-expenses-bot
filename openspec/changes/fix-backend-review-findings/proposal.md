# Proposal

## Why

Ревью бэкенда по ТЗ нашло дефекты, которые проявятся на реальных данных и нагрузке: список трат отдаётся без лимита, бот грузит в память всю историю ради 30 строк, сбой LLM после сохранения траты приводит к дублю, параллельные сообщения одного пользователя гоняются по истории, обновление траты не атомарно. Плюс дыры эксплуатации (нет таймаутов сервера и лимитов на ввод).

## What Changes

- **Пагинация списка трат.** `GET /expenses` получает `limit` (по умолчанию 100, максимум 500) и `offset`, заголовок `X-Total-Count`; репозиторий считает количество и сумму в SQL. Панель показывает постраничную навигацию. Порядок работ: `api/openapi.yaml` → `go generate ./...` → код.
- **`list_expenses` бота без выгрузки всего в память.** Количество и сумма считаются в SQL, строки берутся с `LIMIT 30`.
- **Дубль траты при сбое после инструмента.** Если инструмент уже изменил данные, а следующий вызов LLM упал, факт выполненных вызовов сохраняется в истории диалога, пользователь получает честный ответ вместо «ошибка».
- **Сериализация обработки по пользователю.** Хендлеры `go-telegram/bot` асинхронные (`go r(ctx, b, upd)` в `ProcessUpdate`), сообщения одного пользователя обрабатываются строго по очереди.
- **Атомарное частичное изменение траты** одним SQL-запросом (`UPDATE ... SET поле = COALESCE(...)`), без цикла «прочитал — изменил — записал всё».
- **Очистка протухшей истории диалога** (сейчас карта растёт без ограничения).
- **Таймауты `http.Server` и лимит размера тела запроса.**
- **Лимиты ввода:** длина сообщения пользователя боту и длина `comment` (REST и инструменты агента).
- **Часовой пояс:** `time/tzdata` встроен в бинарь, убран костыль сравнения даты с `time.Now()` в `add_expense`.
- **Индекс** под фильтр по категории.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `rest-api`: пагинация и `X-Total-Count`, лимиты тела и комментария, новые коды ошибок, раскрытие заголовка в CORS.
- `expense-repository`: списки (общий и члена семьи) с пагинацией, количеством и суммой; атомарное частичное изменение.
- `expense-rules`: проверка параметров пагинации и длины комментария, в том числе для операций одного члена семьи.
- `expense-agent`: `list_expenses` с агрегатами из SQL; история не теряет факт выполненных инструментов и очищает устаревшие записи; лимит комментария в инструментах.
- `telegram-bot`: последовательная обработка сообщений одного пользователя, лимит длины сообщения, ответ при частичном сбое.
- `app-bootstrap`: таймауты HTTP-сервера, встроенный tzdata.
- `web-panel`: постраничная навигация списка.

## Impact

- Код: `api/openapi.yaml` + генерация, `internal/database/repository/*` (списки, update), `internal/usecase/*`, `internal/agent/*` (handle_message, history, tools), `internal/transport/http/*`, `internal/transport/telegram/*`, `cmd/app/main.go`, `web/src/*`, `migrations/00003_*`, `docker-compose.yml`, `mock/*` (перегенерация).
- API: `GET /expenses` по умолчанию отдаёт максимум 100 трат (было — все). Клиенты, которым нужны все записи, должны листать.
- БД: новая миграция с индексом по категории.
- Зависимостей новых нет (`time/tzdata` — стандартная библиотека).
