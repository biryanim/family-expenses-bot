# Design

## Context

Мотивация — в `proposal.md`. Состояние кода на момент ревью (подтверждено чтением):

- `ListExpenses` и `ListExpensesForUser` в репозитории строят SQL без `LIMIT`; `tools/list_expenses_execute.go` загружает все траты, считает сумму в Go и режет до 30.
- `go-telegram/bot` v1.27.0: `ProcessUpdate` запускает хендлер как `go r(ctx, b, upd)`, если не включён `WithNotAsyncHandlers`.
- `update_expense` в инструментах делает `GetExpenseForUser` → правка структуры → `UpdateExpenseForUser`, который перезаписывает все четыре поля.

## Goals / Non-Goals

**Goals:**
- Ограничить размер любой выборки и любого тела запроса.
- Не терять факт сохранённой траты при сбое модели; исключить гонки по пользователю и по полям траты.
- Сохранить изоляцию трат: варианты `...ForUser` остаются отдельными операциями.

**Non-Goals:**
- Идемпотентность `add_expense` на уровне БД (ключи дедупликации, уникальные индексы). Защита от повтора — через историю и промпт; полной гарантии нет.
- Курсорная пагинация, сортировки, поиск по тексту.
- Авторизация веб-панели, постоянное хранение истории диалога.
- Рефакторинг, не связанный с найденными дефектами; объединение `X`/`XForUser` (это граница изоляции, а не дубль).

## Decisions

### D1. Страница трат: один метод репозитория с лимитом, смещением и агрегатами
`ExpenseFilter` получает `Limit`/`Offset`; `ListExpenses` и `ListExpensesForUser` возвращают `entity.ExpensePage{Items, Count, Total}`. Количество и сумма считаются тем же запросом оконными функциями (`count(*) OVER ()`, `(sum(amount) OVER ())::bigint`) вместе со строками страницы, поэтому тело и `X-Total-Count` берутся из одного снимка. Единственное исключение — смещение за пределами выборки: строк нет, окно считать не на чем, и тогда (только при `offset > 0` и пустой странице) выполняется второй запрос `SELECT count(*), COALESCE(sum(amount), 0)`. При `offset = 0` пустая страница означает нулевые агрегаты без второго запроса.
- Альтернатива: CTE с `LEFT JOIN` страницы — атомарно всегда, но требует сканировать все колонки траты как nullable и ломает единый `Scan`; отвергнуто ради простоты. Альтернатива 2: всегда два запроса — лишний запрос на каждый список.
- Валидация (`limit` 1..500, `offset` ≥ 0) в usecase, а не в слое транспорта: общая для REST и бота. Новый sentinel `entity.ErrInvalidPagination`, код ответа `invalid_pagination`. Генерируемый сервер границы схемы не проверяет, поэтому `minimum/maximum` в OpenAPI документируют контракт, а проверка живёт в usecase.
- Бот вызывает `ListExpensesForUser` с `Limit=30`: `Count`, `Total` из страницы, `Truncated = Count > 30`. Валидация страницы есть в обоих методах usecase.

### D2. Изоляция трат: `...ForUser` остаются
`GetExpenseForUser`, `UpdateExpenseForUser`, `DeleteExpenseForUser`, `ListExpensesForUser` сохраняются отдельными методами с обязательным `userID`: отличие от общих вариантов (`AND user_id = $2`) — это граница безопасности, а не дубль, и бот физически не может вызвать вариант без фильтра по владельцу. Менять сигнатуры ради схлопывания не нужно.

### D3. Атомарное частичное изменение
`entity.ExpensePatch{Amount *int64, Category *Category, SpentAt *time.Time, Comment *string}`. Репозиторий: `UPDATE expenses SET amount = COALESCE($1, amount), category = COALESCE($2, category), spent_at = COALESCE($3, spent_at), comment = COALESCE($4, comment), updated_at = now() WHERE id = $5 RETURNING ...`; вариант `UpdateExpenseForUser` — тот же запрос с `AND user_id = $6`. Инструмент `update_expense` больше не читает трату перед изменением; валидацию делает usecase над непустыми полями патча. REST `PUT` заполняет все поля патча (семантика «полная замена» из контракта сохраняется, `comment` пустой, если опущен).
- Эффект: бот и панель, меняя разные поля одной траты, не затирают друг друга; одна обращение к БД вместо двух.
- Альтернатива: оптимистичная блокировка по `updated_at`/версии — требует изменения контракта и UI; избыточно для семьи.

### D4. Не терять выполненные действия при сбое модели
В цикле `HandleMessage` агент запоминает результаты изменяющих инструментов (по имени инструмента). Если после этого `CreateChatCompletion` вернул ошибку или исчерпан `maxSteps`, агент: (1) пишет в историю сообщение пользователя и реплику ассистента вида «выполнено: add_expense → 350 ₽, 2026-10-21, id 42», (2) возвращает детерминированный текст «Трата на 350 ₽ записана, но ответить подробнее не удалось» (собирается из результата инструмента кодом, без модели) **и** обёрнутую ошибку. Сигнатура `HandleMessage(...) (string, error)` сохраняется; транспорт при непустом ответе отправляет его, при этом логирует ошибку (ошибку возвращает тот, кто не логирует: логирует транспорт, как и раньше).
- Системный промпт получает правило: если в истории есть запись о выполненном добавлении, а пользователь повторяет то же сообщение, не добавлять заново, а подтвердить.
- Альтернатива: откат (удаление только что созданной траты) — рискованно и тоже может упасть; отвергнуто. Альтернатива 2: уникальный индекс/idempotency-ключ — вне объёма (Non-Goals).
- Известное ограничение: пользователь может явно повторить запись; защита мягкая.

### D5. Сериализация по пользователю в транспорте
Новый тип в `transport/telegram` с мьютексом на `userID`: карта `map[int64]*lock` со счётчиком ссылок под общим мьютексом; запись удаляется, когда счётчик падает до нуля, поэтому память не растёт. Захват блокировки учитывает `ctx` (канал-семафор ёмкости 1 вместо `sync.Mutex`), чтобы ожидающее сообщение отменялось при остановке.
- Альтернатива: `bot.WithNotAsyncHandlers()` — проще, но один зависший вызов LLM (до 30 с × ретраи) блокирует всех пользователей; отвергнуто. Альтернатива 2: воркер-горутина на пользователя — сложнее по жизненному циклу.
- Порядок получения гарантируется порядком, в котором горутины берут блокировку; при почти одновременном приходе строгий порядок Telegram-апдейтов не гарантирован, поэтому спеки требуют «по одному», а не «в точном порядке отправки» для одновременно пришедших.

### D6. Очистка истории без фонового потока
`AppendMessagesForUser` помимо своей записи не чаще раза в `ttl` проходит по карте и удаляет пользователей, у которых все реплики старше `ttl`. Отдельной горутины и её остановки нет; сложность амортизирована.

### D7. Лимиты ввода
Сообщение пользователя > 1000 рун отбивается в `transport/telegram` до `RegisterMember` и агента фиксированным ответом. `comment` > 200 рун — `entity.ErrInvalidComment` в usecase (создание и изменение), код `invalid_comment` в REST, ошибка инструмента модели. Значения — константы в `entity`. Тело HTTP ограничено `http.MaxBytesHandler(next, 1<<20)`; ошибка чтения тела уже превращается в 400 `invalid_request` текущим `HandleRequestError`.

### D8. Часовой пояс
`import _ "time/tzdata"` в `cmd/app/main.go`: +~450 КБ к бинарю, зато поведение не зависит от базы зон в образе. Сравнение строки даты с `time.Now().Format(...)` в `add_expense` заменяется сравнением календарных дат (`date.Date()` против `now.Date()`): действующая спека `expense-agent` («Дата траты») требует, чтобы сегодняшняя дата давала текущий момент, поэтому поведение сохраняется, меняется только способ проверки. Исходное намерение «всегда начало дня» отвергнуто, так как противоречит спеке.

### D9. Индекс по категории
Индекс: миграция `00003_add_expenses_category_index.sql` — `CREATE INDEX expenses_category_spent_at_idx ON expenses (category, spent_at DESC)` (down — `DROP INDEX`). Для семейного объёма выигрыш скромный; делается по требованию ревью, цена — запись одного индекса.

## Risks / Trade-offs

- [`GET /expenses` по умолчанию возвращает 100 вместо всех] → документируется в OpenAPI и README; панель листает страницы; breaking только для внешних клиентов, которых по ТЗ нет.
- [Мягкая защита от дубля (история + промпт)] → описано в Non-Goals; тест сценария повтора проверяет, что в запросе к модели есть запись о выполненном действии.
- [Блокировка по пользователю при зависшей обработке задерживает его следующие сообщения] → таймаут LLM 30 с ограничивает ожидание; блокировка учитывает `ctx`.
- [Пустой `X-Total-Count` за прокси] → панель при отсутствии заголовка показывает навигацию по принципу «есть ли ещё страница» (полная страница = есть следующая).

## Migration Plan

1. Мигратор применяет `00003` до старта `app` (индекс создаётся без блокировки чтения; на семейных объёмах мгновенно). Откат: `make migrate-down`.
2. Деплой — `docker compose up --build`, порядок старта сервисов не меняется.
3. Откат кода — обычный: схема БД обратно совместима (только индекс).
