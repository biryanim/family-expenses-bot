# app-bootstrap Specification

## Purpose

Определяет, как приложение стартует и останавливается: откуда берёт конфигурацию, как реагирует на её ошибки, куда и как пишет логи.

## Requirements

### Requirement: Конфигурация из переменных окружения
Приложение SHALL читать конфигурацию только из переменных окружения: `TELEGRAM_BOT_TOKEN`, `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `DATABASE_DSN` (обязательные), `HTTP_PORT`, `LOG_LEVEL` и `CORS_ALLOWED_ORIGINS` (необязательные). Файлы конфигурации и аргументы командной строки не используются.

#### Scenario: Все обязательные переменные заданы
- **WHEN** приложение запускается с заданными `TELEGRAM_BOT_TOKEN`, `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `DATABASE_DSN`
- **THEN** конфигурация загружается без ошибок и приложение продолжает запуск

#### Scenario: Значение по умолчанию для порта API
- **WHEN** `HTTP_PORT` не задан
- **THEN** используется порт `8080`

#### Scenario: Значение по умолчанию для уровня логирования
- **WHEN** `LOG_LEVEL` не задан
- **THEN** используется уровень `info`

#### Scenario: Значение по умолчанию для CORS
- **WHEN** `CORS_ALLOWED_ORIGINS` не задан или пуст
- **THEN** разрешён только источник `http://localhost:5173`

#### Scenario: Несколько источников CORS
- **WHEN** `CORS_ALLOWED_ORIGINS=http://localhost:5173, http://192.168.1.10:3000`
- **THEN** разрешены оба источника, пробелы вокруг значений и пустые элементы игнорируются

### Requirement: Понятная ошибка при отсутствии обязательных значений
Если хотя бы одна обязательная переменная не задана или пуста (после обрезки пробелов), приложение SHALL завершиться с ненулевым кодом выхода до запуска каких-либо компонентов и вывести сообщение, перечисляющее имена всех незаданных переменных.

#### Scenario: Не задана одна переменная
- **WHEN** приложение запускается без `TELEGRAM_BOT_TOKEN`, остальные обязательные заданы
- **THEN** процесс завершается с ненулевым кодом, а сообщение об ошибке содержит `TELEGRAM_BOT_TOKEN`

#### Scenario: Не задано несколько переменных
- **WHEN** не заданы `LLM_API_KEY` и `DATABASE_DSN`
- **THEN** сообщение об ошибке содержит обе переменные в одном выводе, а не только первую найденную

#### Scenario: Переменная задана пустой строкой
- **WHEN** `LLM_MODEL` задана как пустая строка или из одних пробелов
- **THEN** она считается незаданной и попадает в сообщение об ошибке

### Requirement: Валидация необязательных значений
Если необязательная переменная задана, но её значение некорректно, приложение SHALL завершиться с ненулевым кодом и сообщением, называющим переменную и недопустимое значение. `HTTP_PORT` — целое число от 1 до 65535; `LOG_LEVEL` — одно из `debug`, `info`, `warn`, `error` без учёта регистра.

#### Scenario: Некорректный порт
- **WHEN** `HTTP_PORT=abc` или `HTTP_PORT=70000`
- **THEN** процесс завершается с ненулевым кодом, а сообщение содержит `HTTP_PORT` и переданное значение

#### Scenario: Некорректный уровень логирования
- **WHEN** `LOG_LEVEL=verbose`
- **THEN** процесс завершается с ненулевым кодом, а сообщение содержит `LOG_LEVEL` и переданное значение

### Requirement: Секреты не попадают в логи
Приложение SHALL NOT выводить значения `TELEGRAM_BOT_TOKEN`, `LLM_API_KEY` и `DATABASE_DSN` в логи и сообщения об ошибках.

#### Scenario: Стартовая запись в лог
- **WHEN** приложение успешно загрузило конфигурацию и пишет стартовую запись
- **THEN** запись может содержать порт, уровень логирования, `LLM_BASE_URL` и `LLM_MODEL`, но не содержит значений токена бота, ключа LLM и строки подключения к БД

### Requirement: Структурированное логирование
Приложение SHALL писать логи в stdout в структурированном формате JSON (одна запись на строку) и фильтровать записи по настроенному уровню.

#### Scenario: Фильтрация по уровню
- **WHEN** `LOG_LEVEL=warn`
- **THEN** записи уровней `debug` и `info` не выводятся, записи `warn` и `error` выводятся

#### Scenario: Запись о старте
- **WHEN** приложение успешно запустилось
- **THEN** в stdout выводится JSON-запись уровня `info` о старте

### Requirement: Работа до сигнала и корректная остановка
После успешного запуска приложение SHALL работать до получения `SIGINT` или `SIGTERM`, после чего остановить HTTP-сервер, дав незавершённым запросам до 10 секунд, записать в лог факт остановки и завершиться с кодом 0.

#### Scenario: Остановка по SIGTERM
- **WHEN** запущенному приложению отправлен `SIGTERM`
- **THEN** HTTP-сервер перестаёт принимать новые соединения, в лог пишется запись об остановке и процесс завершается с кодом 0

#### Scenario: Запрос в момент остановки
- **WHEN** `SIGTERM` приходит, пока обрабатывается запрос к API
- **THEN** запрос завершается с обычным ответом, после чего процесс завершается

### Requirement: Подключение к БД при старте
После загрузки конфига приложение SHALL подключиться к PostgreSQL по `DATABASE_DSN` и проверить соединение. Только после этого приложение считается запущенным. Приложение SHALL NOT применять миграции схемы само.

#### Scenario: БД доступна
- **WHEN** приложение запускается, и PostgreSQL по `DATABASE_DSN` доступен
- **THEN** в лог пишется запись уровня `info` об успешном подключении, и приложение продолжает запуск

### Requirement: Остановка при недоступной БД
Если подключиться к БД не удалось, приложение SHALL записать ошибку в лог и завершиться с ненулевым кодом, не запуская остальные компоненты. Сообщение об ошибке SHALL NOT содержать пароль из `DATABASE_DSN`.

#### Scenario: БД недоступна
- **WHEN** по адресу из `DATABASE_DSN` нет работающего PostgreSQL
- **THEN** процесс завершается с ненулевым кодом, а в логе есть запись уровня `error` о неудачном подключении без пароля

#### Scenario: Некорректная строка подключения
- **WHEN** `DATABASE_DSN` содержит пароль, но синтаксически некорректна
- **THEN** процесс завершается с ненулевым кодом, а сообщение об ошибке не содержит пароля

### Requirement: Миграции до старта приложения
При запуске одной командой `docker compose up` миграции схемы SHALL применяться отдельным шагом до старта приложения. Если миграции завершились ошибкой, приложение SHALL NOT стартовать.

#### Scenario: Запуск на чистой БД
- **WHEN** `docker compose up` выполняется с пустой базой
- **THEN** сначала применяются все миграции, затем стартует приложение

#### Scenario: Ошибка миграции
- **WHEN** шаг миграций завершился с ошибкой
- **THEN** приложение не запускается, а в логах шага миграций видна неудачная миграция и причина

### Requirement: HTTP-сервер API
После подключения к БД приложение SHALL поднять HTTP-сервер REST API на порту `HTTP_PORT` на всех интерфейсах и записать в лог уровня `info` адрес, на котором он слушает. Если порт занять не удалось, приложение SHALL записать ошибку в лог и завершиться с ненулевым кодом.

#### Scenario: Сервер запущен
- **WHEN** приложение запустилось с `HTTP_PORT=8080`
- **THEN** `GET http://localhost:8080/api/expenses` отвечает 200, а в логе есть запись о старте HTTP-сервера на порту `8080`

#### Scenario: Порт занят
- **WHEN** порт `HTTP_PORT` уже занят другим процессом
- **THEN** процесс завершается с ненулевым кодом, а в логе есть запись уровня `error`
